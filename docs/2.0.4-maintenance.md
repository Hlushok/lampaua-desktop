# Підготовка спільного оновлення після 2.0.3

Статус: гілка-кандидат, не опублікований реліз. Production runtime і канал
автооновлень залишаються на перевіреній 2.0.3 до нового приймання.

## Інтеграція Донора

Kolovatoff `f834fec95c22c6391c8e285cb2b769754c24df73`:
IINA autoplay через існуюче `playlist_next`, macOS native fullscreen,
донорські URL-тести та наші window-manager regression tests.
Внутрішні переходи kinohub.uk/legacy HTTP, MPV attach/close deadlines,
профіль і appId збережено. Windows/Linux fullscreen-параметри не змінено.
Electron 45 і ESLint 10 не відкотили до старіших версій донора.
Фізичний macOS/IINA playback потребує окремої платформенної перевірки;
Windows VM-тести не видаються за неї.

## Залежності І Безпека

Перенесено зміст PR #21: updater 6.8.11, builder 26.18.0, rolldown 1.2.15.
`yarn up -R` оновив лише сумісні діапазони security-залежностей:
fast-uri 3.1.9, js-yaml 4.3.2, xmldom 0.8.15, humanfs/node 0.16.8,
brace-expansion, http-cache-semantics і підтримувані гілки undici.
Нема blanket major resolutions, заміни ffmpeg.dll або переходу на Node 26.

До оновлення: production 11 advisory у fast-uri/js-yaml;
full graph 39 унікальних advisory. Після оновлення обидва audit без
deprecation warnings пройшли без advisory. Депрекації boolean/glob/inflight,
lodash.isequal і rcedit не приховуються у звичайному audit.
`--no-deprecations` відокремлює їх від advisory, не ігнорує вразливості.

## CI

Зафіксовано перевірені Actions: checkout 7.0.1, setup-node/python 7.1.0,
upload-artifact 7.0.2, download-artifact 8.0.2, action-gh-release 3.0.3.
Artifact digest mismatch явно завершує download помилкою; multi-file ZIP
artifacts і read-only candidate build permissions збережено.
Node проєкту залишається 24, Yarn 4.18.1. Нема залежності від dummy
NODE_AUTH_TOKEN, видаленого в setup-node 7; pip-install input не використовується.
Dependabot тепер пропонує CI major-оновлення для review, але не мерджить
і не публікує їх автоматично. npm major ignore збережено.

Нові node tests, production security audit і `verify-ci-maintenance.cjs`
увімкнені у validation, sync та Windows release gates.
Спільна update-гілка запускає validation і окрему macOS test build CI;
ці workflow не публікують реліз і не змінюють updater metadata.

## Кандидат Нового Ядра

Новий artifact-only variant `d3d11-next` має окремі source lock, каталоги
і назви artifacts; `baseline` та прийнятий `d3d11` не змінено.
MPV `82667e3c`, FFmpeg `86444dd3`, рецепти shinchiro `1f8d2e76` зафіксовано
повними commit SHA. Решта 89 source pins збережені. У тому числі ANGLE
залишається зафіксованим, хоча donor recipe видалив свій старий reset.

MPV вже містить D3D11 render API 2.6, тому `nativeD3d11: true` вимагає
порожнього списку backport patches. До компіляції перевіряються API,
header/backend, чистота джерел, source archives та effective-tree hashes.
Базове й фактично використане дерево джерел архівуються, як і раніше.
Native provenance включено в manifest, candidate SDK receipt та source audit.

Перевірено мінімальні вимоги нового MPV: libplacebo >=7.360.1 (наш pin:
7.374), Vulkan >=1.4.309 (headers 1.4.365), subrandr >=1.1.0 (наш pin:
1.4.0). Новий FFmpeg використовує libavcodec/libavformat major 63;
це внутрішня залежність власної DLL, не заміна Chromium ffmpeg.dll.
GitHub compare FFmpeg обрізає список, тому аудит не означає повного
ручного перегляду всіх 879 commit. Остаточна сумісність доводиться
компіляцією, перевіркою джерел і playback acceptance.

Підготовка нового recipe локально успішна. 90 Python tests, workflow/native
metadata checks і lint пройшли. Validation 40554085686 та IINA/macOS build
40554086063 для donor/dependency merge також успішні.

Запуск DLL CI: `build-libmpv.yml`, update branch, `variant=d3d11-next`,
`target=mpv`. Це лише artifacts; production pins, теги, реліз і updater
metadata не змінюються. Після збирання використати `audit_runtime_sources.py
--variant d3d11-next` і `verify-mpv-d3d11-native.cjs --variant d3d11-next`
із точним build commit. Прийняття старої DLL не поширюється на нову.

Перший candidate run 40555733449 зупинився до checkout/компіляції:
GHCR видалив старий donor container digest (`manifest unknown`). Для нового
variant зафіксовано доступний Linux amd64 образ від 23 жовтня:
`sha256:ce439d0f03419bd2c022dd3746a3a9a15b2f1f4a73b47f975a02734992ba1383`.
Manifest bytes перевірено за SHA-256, platform прочитано з verified config blob.
Історичні source configs не переписано. Окремий host CI job тепер перевіряє
доступність і digest образу до створення container job; немає floating latest
fallback. Видалення donor image надалі потребує явного review нового pin.

План: `superpowers/plans/2026-10-27-desktop-unified-update.md`.

## Перевірка 29 Жовтня

Звірено план, чисту update-гілку b05c234 і поточний donor f834fec.
GitHub validation 40556594250 та IINA/macOS 40556594500 успішні.
Плановий sync 40667554836 ще використовує старий main e9acfed і зупиняється
на вже інтегрованих у candidate package/window-manager змінах. Це не збій
встановленого додатку. Правила ручного перегляду не послаблювалися.

DLL run 40556592535 пройшов перевірку контейнера, 94 source tests і capture
preflight, але після збирання залежностей FFmpeg відхилив застарілий параметр
`--enable-opengl`. У рецепті лише нового native-кандидата цей параметр вилучено;
MPV D3D11/OpenGL backends, старі configs і production runtime не змінені.

Тепер CMake зберігає точний масив configure arguments у project receipts.
Перед GCC новий candidate викликає parser зафіксованого FFmpeg із `--help`
останнім аргументом, у тимчасовій теці. Це перевіряє опції без compiler/library
probes; ранній `--help` або `--list-*` у recipe відхиляється. Кінцева перевірка
бібліотек і лінкування все одно виконується під час справжньої компіляції.

На точному FFmpeg локально відтворено `Unknown option "--enable-opengl"`;
після вилучення одного параметра всі 64 recipe options прийняті. 99 Python
tests, 18 donor/navigation tests, workflow contracts, lint і production audit
пройшли. Окремо перевірено наявність усіх 42 packages у production dependency
graph раніше запакованої Windows test build. Ця збірка має стару прийняту DLL
і не є доказом приймання `d3d11-next`.

Виправлення закомічене як 3761a32 і запушене лише в update-гілку.
Новий artifact-only run: 40929887820. Validation 40929887735 та IINA/macOS
40929887774 успішні. Production main/tag/runtime не змінені.

Проміжний packaged QA на попередній DLL також успішний: 4K HEVC,
H264/AAC, MKV AC3/EAC3, AVI/Xvid/MP3, pause/seek/volume/speed,

screenshots переглянуто. Закриття 848 мс, production profile без змін.

або 80+ GB TorrServer. Вбудована навмисна перевірка неіснуючого зовнішнього
плеєра може показати відповідне повідомлення; це не decode failure відео.

## Упаковка Нового Кандидата

Після успішного DLL/source audit створити перевірений
`build/libmpv-d3d11-next-test.json` із точними SHA та build commit, за форматом
старого test receipt. Не копіювати старі hashes і не використовувати вигадані
значення. До появи цього файла збірка нового кандидата навмисно заборонена.

Команда: `node scripts/build-win-mpv-test.cjs --d3d11-next --candidate-sdk PATH`.
Можна додати `--stage-only` або `--unpacked`; `--release` і змішування
`--d3d11`/`--d3d11-next` відхиляються. Нові каталоги:
`.cache/mpv-desktop-d3d11-next-test` та `dist/mpv-desktop-d3d11-next-test`.
Профіль `LampaUaDesktopMpvD3d11NextTest` відокремлений і від production,
і від попередньої D3D11 test build; її авторизація автоматично не переноситься.
QA: `verify-mpv-desktop.cjs --d3d11-next --exe PATH` зберігає окремі докази
й відхиляє старий test package. Для live YouTube потрібна власна авторизація
користувача в цьому новому тестовому профілі.

Зіставляються SDK/source/DLL/effective-tree SHA, provenance notices inventory
і всі файли notices. Native candidate не отримує старий backport patch.
Звичайні release pins/paths та legacy `--d3d11` збережені. CLI, ізоляція,
renderer/release contracts, lint і повна old-SDK stage-only перевірка пройшли.
Це готовність інструментів, а не приймання ще не зібраної DLL.

Незалежне рев'ю змін до 5f730f3 знайшло одну помилку лише в QA:
після navigation recovery новий кандидат читав журнал старого test profile.
Шлях виправлено; regression виконує фактичне читання для 8 комбінацій
old/next, persistent/run-id і release profile. RED до виправлення, GREEN
після, результат незалежно підтверджено. Інших підтверджених дефектів коду
не виявлено. Lint, isolation, D3D11 integration і release contracts пройшли;
validation 40931989759 та IINA/macOS 40931989753 для 5f730f3 також успішні.
Це не замінює source audit нової DLL і реальний тривалий 4K playback.
