# Пряме Direct3D 11 виведення MPV у LampaUa Desktop

Дата: 2026-10-21. Стан: схема підготовлена для перевірки користувачем;
реалізація ще не розпочата. Користувач погодив вибір MPV із прямим D3D11 API,
а не окремого Windows-рушія Flyleaf.

## Мета та межі

Плавне вбудоване відтворення 4К у повній Windows x64 LampaUa Desktop без
індивідуальних параметрів для фільмів. Зберігаємо каталог, панель Lampa,
перемотування, звук, доріжки, субтитри, позицію перегляду та чинну маршрутизацію
YouTube, IPTV, інших плагінів і зовнішніх плеєрів.

Змінюється Windows-шлях виведення кадрів, не весь додаток. Windows UA Player,
Android, встановлений Desktop і його профіль, Lampac, JackTor та VPS не змінюються.
Немає серверного транскодування, прив'язки налаштувань до URL/назви/розміру
торента, примусового зменшення якості джерела або нового каналу автооновлень.
Публікація, push і тег потребують окремого дозволу.

Результат реалізації для користувача: повний локальний тестовий Desktop з окремим
профілем, не окремий mpv-плеєр або самотня DLL. Поки критерії нижче не пройдені,
тестова версія не замінює робочу.

## Підстава вибору

У Windows UA Player Flyleaf використовує спільний D3D11 device для декодування
та GPU-обробки; підготовка кадру відокремлена від його показу через swapchain.
Чинний Desktop використовує `d3d11va-copy` → CPU RGBA → IPC → WebGL upload.
Це різні шляхи, а не доказ браку загальної потужності процесора.

Поточна DLL через native D3D11 VO пройшла короткий 4К-тест без пропусків, але
такий окремий native-вихід не є інтеграцією кадрів у вікно Lampa.
ANGLE-прототип із трьома текстурами не пройшов критерії: ~20 доставок/с при 24
кадрах/с і 35 пропусків. Деталі: `docs/4k-playback-performance.md`.
CPU-тривалість виклику render не дорівнює часу завершення GPU-роботи.

Розглянуті варіанти:

1. Прямий D3D11 render API MPV: обраний користувачем. Зберігає MPV, facade
   Lampa та браузерний UI, прибирає software RGBA/WGL/ANGLE із GPU-шляху.
   Потребує нової DLL і перевіреного передавання GPU-текстур у Electron.
2. Native-вікно MPV: доступне в нинішній DLL, але накладання панелі Lampa,
   hit-testing, fullscreen і z-order потребують іншої інтеграції вікон.
   Не використовуємо як непомітну заміну погодженому render API.
3. Flyleaf: робочий довідковий рушій UA Player, але нова Windows-підсистема з
   окремими залежностями. У цю реалізацію не входить.

Вибір D3D11 не гарантує успіх мосту Electron. Якщо окремий native render швидкий,
а повний Desktop ні, спочатку діагностуємо транспорт/показ, а не змінюємо кодеки
чи нескінченно збільшуємо кількість текстур.

## Нова DLL без супутнього оновлення всього стека

Базова MPV-ревізія залишається
`36bf3d529059a947d6700adefeab3b421e537c19`, FFmpeg —
`5d4755f7dd03d84f006d5a0ef7e3c114f52b3d77`. Recipes, container і dependency lock
також залишаються зафіксованими, якщо попередня перевірка не доведе конкретної
необхідної несумісності. У такому випадку зупиняємося й окремо погоджуємо
розширення обсягу, не переходимо автоматично на рухомий master.

Переносимо upstream-коміт
`4255130de410e0cbdab694b951085409d466b704` від 2026-10-15:
`libmpv: add D3D11 render API backend`. Це 8 файлів, 251 додавання / 5 видалень.
`git apply --check` на копії нашої бази 2026-10-21 пройшов без конфліктів;
сам патч під час підготовки схеми не застосовувався.

SHA-256 отриманого upstream patch:
`24c70218104aeae57ecf733b3ac6787314aaa8e7e1bf332f7bb4bec185ac4217`.
Патч, базові джерела, точні залежності, build scripts і всі локальні зміни
мають увійти у corresponding sources нової DLL. Маніфест має відрізняти базовий
commit від застосованої patch series й містити хеш ефективного дерева джерел.
Перевірки source closure не послаблюємо. Нову DLL не видаємо за незмінний upstream.

Перший артефакт — кандидат в окремому кеші з власним SDK, import library,
SHA-256 і маніфестом. Чинний `build/libmpv-runtime.json`, прийнята DLL та старий
комплект джерел не перезаписуються до завершення перевірок. Кандидат повинен
підтвердити client API 2.6 і реально створити D3D11 render context; одного
наявного заголовка або експортів недостатньо.

На цій Windows-машині перевірка `wsl --list --quiet` повернула порожній список;
Docker не знайдений у PATH. Під час планування реалізації потрібно обрати
доступне середовище довгої cross-збірки. Ця схема не дозволяє непомітно
встановлювати WSL/Docker або запускати зміни на VPS. Збірка в GitHub Actions
можлива лише після окремого дозволу на потрібний push/CI, без релізу додатка.

## GPU-шлях і потоки

Потік даних:

```text
HTTP/HTTPS → demux/decode MPV → D3D11 texture
→ MPV D3D11 render на тому самому device → shared GPU texture
→ Electron VideoFrame → GPU-композиція з панеллю Lampa
```

Декодер запитує `auto-safe`, а фактичний `hwdec-current` обов'язково журналюється.
Для підтримуваного HEVC тесту очікуємо `d3d11va`, не `d3d11va-copy` або `no`.
Для непідтримуваних апаратно кодеків MPV може декодувати програмно, але
масштабування/кольори/виведення лишаються на GPU, якщо GPU backend справний.

Native-адаптер створює D3D11 hardware device без SINGLETHREADED, із BGRA support
та потрібним multithread protection. Device використовується і MPV, і render
targets; adapter LUID фіксується для порівняння з GPU Electron, особливо на
ноутбуках із двома відеокартами. WARP не називаємо апаратним успіхом.

Ініціалізація, render/update/get-info, GPU-очікування та звільнення D3D11 render
context виконуються на виділеному native render thread, не Electron main або
renderer UI thread. Async-фабрика повертає main готовий NativePlayer; preload
`create()` уже є Promise-контрактом і лишається таким. Event pump та чинна
обмежена черга async-команд MPV зберігаються. Контекст не використовується
одночасно з кількох потоків; cleanup не випереджає активну GPU-роботу.

Native-декодування й CPU/RGBA fallback не змішуються непомітно. Windows GPU
backend отримує окремий внутрішній ідентифікатор `d3d11`; старі software та
macOS shared-texture шляхи залишаються окремими.

## Кадри, синхронізація та ресурсні межі

На першому етапі пул обмежений трьома GPU-слотами. Розмір текстури відповідає
площі виведення з DPR, до 3840x2160, без старого software-ліміту 1920x1080.
Пул не росте через повільне звільнення кадрів. Для resize допускається лише
одне додаткове покоління до звільнення старого; подальші resize об'єднуються.

Кожен слот має session id, generation, frame sequence, target timestamp,
frame flags та стани FREE → RENDERING → READY → READING → FREE. Старі кадри
після seek, нового source, resize або destroy відхиляються за generation.
Підтвердження іншої сесії/власника або повторний ack не звільняє ресурс.

MPV малює прямо в D3D11 render target, без CPU Readback/RGBA IPC і без WGL/ANGLE.
Між різними devices використовується документована D3D11 синхронізація
(keyed mutex / GPU completion), не лише факт повернення CPU-виклику.
Слот не перезаписується, поки GPU Electron ще читає його.

Передавання — через публічний Electron sharedTexture API. Якщо wrapper
`sendSharedTexture` відтворює вже спостережену втрату IPC, використовуємо
документовані `startTransferSharedTexture`, `finishTransferSharedTexture`,
creation/release sync tokens і власний вузький авторизований IPC-контракт.
Жодних приватних назв каналів Electron, `_linkedBinding` або підміни runtime.
Точний маршрут визначається коротким transport-gate до повної інтеграції;
публічний transfer path є обов'язковим резервним кандидатом, не дозвіл
ігнорувати помилку wrapper.

Renderer закриває кожен VideoFrame та відпускає імпорт у `finally`, із release
callback/token для native-власника. Release означає безпеку повторного запису,
а не факт фізичного показу. Очікування завершення всієї WebGPU queue після
кожного кадру не серіалізує підготовку всього пулу. Повторне використання
імпортів допускається лише після доказу коректної міжкадрової синхронізації.

Час показу визначається MPV/audio clock і target timestamp. Блокування до
target time дозволене лише на render thread. Вимірюємо render submission,
GPU completion, приймання, upload/submit та compositor cadence окремо.
`report_swap` не викликається за простим IPC ack або `onSubmittedWorkDone`:
ці події самі по собі не доводять VSync/physical present. Не вмикаємо
display-resample на основі вигаданих swap timestamps. Одиниці часових міток
перевіряються саме на кандидатній DLL, не виводяться лише з коментаря заголовка.

## Колір, керування та відмови

Початковий сумісний вихід — BGRA8 SDR із GPU tone mapping для HDR-джерел і
узгодженим colorSpace. Це не обіцянка HDR passthrough або підтримки всіх
Dolby Vision metadata; такі можливості потребують окремих display-тестів.
Немає вимкнення HDR/DV за назвою конкретного фільму. Аудіодоріжки, AC3/EAC3,
субтитри й протокольний whitelist не змінюються.

Device creation failure, відсутній API або WebGPU/sharedTexture повертають
керовану помилку й одноразовий software fallback із збереженням source, headers,
позиції, pause, volume, speed, audio/subtitle selection. Цей fallback може бути
повільним у 4К, тому його не видаємо за успішний D3D11-тест. Для live потоку не
робимо довільний seek у стару часову позицію. Захист від циклу fallback обов'язковий.

Навігація, закриття renderer, device removed, скасований open/seek і тайм-аут
release не блокують панель чи вихід. Ресурс із невизначеним станом GPU не
звільняється тільки через сплив таймера; transport закривається, публікація нових
кадрів припиняється, а retirement чекає підтвердженого завершення/втрати device.
Повторна ініціалізація не нарощує кількість таких поколінь без обмежень.

IPC залишається обмеженим головним frame дозволеного вікна та власником сесії.
Не відкриваємо сторінці довільні native handles, файлові шляхи або mpv-команди.
У вимірювальний журнал не пишемо signed URLs, торент-хеші, cookies або токени.

## Контрольні етапи

1. Відтворювана кандидатна DLL: source preflight, відповідні джерела, checksum,
   API/context test; старі артефакти залишаються доступними для відкату.
2. Native D3D11 render-thread тест: правильні кадри й завершення GPU-роботи,
   порівняння з native VO на тому самому локальному файлі.
3. Transport-gate без Lampa: відомі змінні D3D11 кадри з sequence marker,
   не менше 60 с показу, перевірка пропусків/порядку/IPC/очищення. Якщо шлюз
   не проходить, не витрачаємо час на маскування проблеми в Lampa.
4. Повна LampaUa: каталог, керування, routing, fullscreen, resize, повторні
   запуски, помилки/відновлення, профіль та завершення процесів.
5. 4К-приймання й передача локального готового Desktop користувачу.

Для performance-замірів немає паралельних збірок, інших плеєрів або зміни
параметрів під окремі ролики. Використовуємо безперервний fixture, а не MP4
із loop-стиками. Пошкоджений 2259-byte BDRemux sample не є fixture.

## Критерії приймання

- 4К HEVC 8/10-bit, SDR/HDR, звичайне відео та швидкий рух: після warmup
  щонайменше 98% унікальних кадрів джерела за кожні 30 с, не більш як один
  новий renderer drop і decoder drop, нормальний clock ratio 0.98–1.02.
- Немає пауз між новими кадрами понад три source frame intervals плюс один
  display interval; UI тримає щонайменше 90% свого idle RAF baseline.
  Доставка, GPU submission і physical-present evidence не змішуються.
- Підтверджені непорожні змінні пікселі та frame sequence, не тільки кількість
  callback. Скриншоти і візуальна оцінка руху обов'язкові, але не замінюють метрик.
- А/В синхронність перевірена метриками та синтетичним lip-sync/click fixture;
  після warmup абсолютний avsync не перевищує 50 мс у стабільному відтворенні.
- Той самий 86.47-ГБ торент на 25:10–25:30 та щонайменше три хвилини навколо:
  без slow-motion/ривків. Реальний потік потрібен окремо; недоступність потоку
  не перетворює синтетичний успіх на закритий користувацький дефект.
- H264/AAC, AC3/EAC3, доріжки/субтитри, YouTube DASH, IPTV HLS/TS, HTTP headers
  плагінів, зовнішній UA Player і browser routing проходять чинні контракти.
- Щонайменше 50 циклів open/seek/close, зміна розміру й fullscreen, навігація,
  renderer crash і device failure: немає deadlock, необмеженого росту handles,
  textures чи пам'яті, подвійного free та кадрів після destroy.
- Поточні syntax, `yarn lint`, source preflight, native lifecycle, ownership
  і protocol tests та повний smoke проходять на фінальній повній тестовій збірці.
- Робочий профіль незмінний, autoUpdater ізольований, встановлена програма
  не замінена, нової публікації немає.
